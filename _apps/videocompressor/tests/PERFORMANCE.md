# 성능 확인 및 개선 결과

측정일: 2026-10-08 (한국 시간). AMD Ryzen 5 5600U, 논리 CPU 12개, 시스템 표시 메모리 약 14GiB, Windows Edge 154.0.4258.62 헤드리스. FFmpeg core 0.12.10 단일 스레드. 로컬 HTTP 서버에서 실행했습니다.

## 결론

기존 기본 설정은 긴 고해상도 영상을 빠르게 처리하기에 느립니다. 2패스 fast 인코딩이 병목이었습니다. 자동·극한 모드에 veryfast 프리셋을 적용해 이번 샘플에서 인코딩 시간을 약 40% 줄였습니다. 화질 우선 모드는 기존 fast를 유지합니다. 중복 입력 읽기·분석을 제거하고, WORKERFS로 전체 입력의 ArrayBuffer/MEMFS 복사를 피했습니다. 진행률 UI는 최대 약 10회/초로 갱신하고 압축 시작 시 원본 미리보기 재생을 일시 정지합니다.

## 실측

모두 30FPS, 원본 해상도 유지, H.264 MP4, 목표 2,000,000바이트, 동일한 2패스 정책입니다. FFmpeg testsrc2로 만든 움직이는 패턴을 ultrafast CRF18 MP4로 인코딩한 약 12MB 입력을 사용합니다. 입력 생성·화질 비교 시간은 압축 시간에서 제외합니다.

| 입력 영상 | 기존 코드 fast | 개선 코드 veryfast | 단축 | 실제 결과 크기 |
|---|---:|---:|---:|---:|
| 1280×720 / 10초 | 28.66초 | 17.60초 | 38.6% | 1,936,303바이트 |
| 1920×1080 / 5초 | 30.34초 | 18.10초 | 40.3% | 1,933,963바이트 |

개선 코드에서 fast와 veryfast를 같은 실행 안에서 비교해도 각각 29.07→17.60초, 30.26→18.10초로 약 40% 차이가 났습니다. 기존 코드는 `performance-baseline.json`, 개선 후 결과는 `performance-results.json`에 저장했습니다. 개선 코드의 반복 prepare는 측정 정밀도 내 0ms로 반환했으며, 기존 코드는 약 13ms가 추가됐습니다. 두 샘플 모두 WORKERFS가 활성화되었고, File.arrayBuffer를 호출하면 실패하도록 설정한 상태에서 분석과 인코딩이 성공했습니다.

| 입력 | fast SSIM | veryfast SSIM |
|---|---:|---:|
| 720p | 0.986997 | 0.986837 |
| 1080p | 0.987920 | 0.987796 |

SSIM은 동일 입력 대비 비교한 지표입니다. 이 합성 샘플에서 차이는 작았지만 실제 얼굴·글자·어두운 영상 등 모든 콘텐츠의 동일한 화질을 보장하지 않습니다. veryfast 결과가 목표 용량 미만인지 실제 바이트로 검증했습니다.

인코딩 중 50ms 간격의 메인 스레드 타이머를 실행했습니다. 개선 결과의 최대 간격은 약 64.5~65.1ms로, 측정 경로에서 긴 UI 스레드 정지는 관찰되지 않았습니다. 이는 브라우저 이벤트 루프 지연 측정이며 실제 모바일 터치 지연을 검증한 결과는 아닙니다.

## 남은 한계

- 이 PC에서도 10초 720p 영상은 약 18초, 5초 1080p는 약 18초가 필요했습니다. 실시간보다 빠른 처리를 보장하지 않습니다. 영상 길이뿐 아니라 해상도, 프레임 수, 장면 복잡도, 코덱, 재압축 횟수에 따라 달라집니다.
- 고해상도 원본을 디코딩하는 비용은 출력 해상도를 낮춰도 남습니다. 낮은 목표 용량으로 인한 재압축은 추가 시간이 걸립니다.
- 두 패스를 한 패스로 바꾸면 화질·용량 제어 정책이 달라지므로 이번 개선에서는 2패스를 유지했습니다.
- 멀티스레드·WebCodecs 하드웨어 가속 엔진은 추가하지 않았습니다. 큰 성능 향상을 더 요구하면 별도 엔진 모듈과 실제 브라우저별 검증이 필요합니다.
- 코어 최초 초기화는 로컬에서 약 255ms였으나 인터넷에서 약 32MB WASM을 처음 받는 시간은 포함하지 않습니다. 최초 다운로드는 네트워크에 영향을 받습니다.
- 입력 전체 복사는 피하지만 디코더·인코더·출력 메모리는 여전히 필요합니다. 프로세스 전체 피크 메모리와 모바일 메모리 부족은 실측하지 않았습니다. WORKERFS가 지원되지 않는 경우 기존 복사 방식으로 대체합니다.
- 수치는 각 조건 1회 실측이며 통계적 p95, 저사양·모바일 기기, 장시간 열 제한을 대표하지 않습니다. 성능 목표의 확정에는 대표 실사용 영상과 대상 기기가 필요합니다.

## 재현

```sh
npm ci
npm run build
node tests/performance.mjs
npm test
node tests/browser-smoke.mjs
```

Windows Edge 기본 경로가 다르면 EDGE_PATH 환경 변수를 지정합니다. 성능 스크립트는 소스 모듈을 로컬 서버에서 불러와 측정하며 결과 JSON을 쓰기 전에 기존 결과를 `_BU` 이름으로 백업합니다. CPU를 사용하는 다른 프로그램을 줄이고 실행하세요.

성능 개선 후 단위 테스트 9개, Vite 빌드, 실제 압축·음성 AAC·취소 후 재시작·320px 화면·오프라인 압축 회귀 검증을 수행했습니다. 원본 전체 복사 방지, 동일 File의 분석 재사용, WORKERFS 미지원 대체 경로와 취소 시 상태 제거도 테스트합니다.

WORKERFS 기능은 [ffmpeg.wasm 공식 사용 문서](https://ffmpegwasm.netlify.app/docs/getting-started/usage/) 및 설치한 패키지의 Worker 구현을 확인했습니다.
